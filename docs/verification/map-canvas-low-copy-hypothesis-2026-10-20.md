# Bounded Canvas map hypothesis — 2026-10-20

This is a read-only architecture audit and next experiment proposal. No renderer was implemented, no browser benchmark was run, and the full-map 60 fps gate remains open. Reviewed production `assets/js/graph.js` and the hardware, retained-layer and scene-GPU follow-ups, including their explicit resource/timing limitations.

The saved controlled Canvas hardware artifact gives a more precise explanation than “the cache is slow.” In light 1440×1000/DPR2, overview zoom performs seven full paints during 24 input frames; draw p50 is approximately 0.1 ms, paint p95 is 16.8 ms, and draw max is 26.2 ms, yielding 50.319 fps. Detail zoom likewise performs seven paints, with draw p50 approximately 0.1 ms, paint p95 7.6 ms, draw p95 10.5 ms and 47.812 fps. Detail pan uses the same peak 11,274,752-pixel raster yet reaches 60.002 fps with one full paint in 61 draws. These are values in `map-hardware-performance.json` → `controlledCanvas.results`, not new measurements.

Production `_draw()` reuses a padded raster only while coverage, exact key, the four LOD tiers and the 0.6–1.8 scale interval permit. The sinusoidal zoom crosses actual tier boundaries and changes coverage/scale, so seven paints rather than one are expected. Every reuse still clears the visible Canvas and scales/copies the cached Canvas with `drawImage`. Native text, already included in that raster, is also reprojected. Rebuild costs demonstrably exceed a frame in the overview case. The detail figures show that short JS submission intervals do not establish cheap presentation: copy/composition, asynchronous raster work, driver scheduling and benchmark drain behavior remain plausible contributors. The existing data does not identify one of those as the sole cause.

The rejected GPU retained experiment does not remove that uncertainty for Canvas. Its 12 cache builds and 30.3% normal uncovered area, plus 92.2% oversized uncovered area, still invoke the expensive edge subsystem; its GPU timer omission experiment identifies that subsystem only within its different renderer and bounded diagnostic conditions. Neither experiment supports increasing resolution error, dropping pixels, changing same-style stroke union or inflating a memory budget to claim success.

## One concrete next hypothesis

Test **connected retained Canvas composition**, only for the already cache-eligible normal unselected moving view. Promote the retained geometry Canvas itself to a clipped, `pointer-events:none` DOM layer; reuse it by updating its CSS transform instead of copying its pixels into the main Canvas on each cache hit. Keep ordinary Canvas native painting, the existing world coordinates, closure/hit logic and native input handlers. This is a bounded experiment in composition rather than a new scene renderer.

Preserve the painter's actual order with three connected layers: (1) backgrounds and region/chapter/collection words in their existing before-edge order, painted at the exact current transform; (2) cached edges and nodes transformed as a unit; (3) exact current native node labels/rings requiring after-node order, using the original stable input Canvas. Merely overlaying every label on one transformed complete-picture Canvas would reorder titles relative to edges and double-paint words; it is not the proposed candidate. Splitting emphasized closure rendering is out of this first experiment's scope: hover/selection should invalidate the CSS layer and use the complete existing Canvas path until separately demonstrated correct.

Two extra backings must share the existing 16,000,000-pixel bound. At actual normal map W=1440,H=932,DPR2, an unpadded decoration underlay costs 5,368,320 pixels. A geometry pad of 224 CSS px costs (1888×1380×4)=10,421,760, totaling 15,790,080, below the cap. The existing 256 px pad plus that underlay would exceed it. Compute this dynamically with the original 8192-edge constraint; retain no layer if it cannot fit. Main Canvas and browser compositor copies remain explicitly outside the existing logical bound, so this is not a total physical/GPU memory claim. The oversized full-resolution direct fallback remains required. No new permanently duplicated screenshot/bitmap/texture is hidden outside the accounting.

The CSS transform must use the existing cache origin, pad, current/source scale and physical-pixel translation convention. CSS transforms do not promise Canvas-identical resampling; that is a hypothesis to test, not an accepted equivalence. Native words must remain connected, unscaled, current-font/current-phase, and be recomputed when current layout/collision rules change. On settle, remove the transform/layer presentation and perform the exact full-resolution native paint. Fonts, theme, filters, highlight, resize/DPR, destruction and pointer cancellation invalidate or release every extra layer. Since coverage/LOD rebuilds remain, this may still fail the performance gate; do not broaden it preemptively.

## Falsification and acceptance plan

First add test-only operation counters, without any timings, to distinguish cache hit, scale/LOD/coverage invalidation, original-painter calls, main-canvas clear/copy and CSS transform writes on the exact saved wheel sequence. A cache hit should have zero geometry repaint and zero full-frame raster copy; all seven expected boundary rebuilds remain honestly reported. Verify inventory and immutable source/data hashes.

Then compare complete intermediate and settled screenshots against the original complete `_paint()` at identical transforms, in both themes/DPR1/2, narrow/normal/oversized regimes, including all LOD boundaries, extreme permitted reprojection scales, fractional translations, uncovered edges and real fonts. Use the established full-frame mean<2/255 and >20-channel fraction<2% limits without omission masks, and personally inspect title/edge ordering, node labels, rings and clip boundaries. Settled direct fallback must remain exact; moving bounded errors must be named. Check all actual backing sizes and lifecycle release, all original native wheel/pinch/pan/keyboard/reset/selection/filter/highlight/tooltip and linear-oracle hit semantics; actual full canvases must be active and nonblank before reading pixels.

Only after correctness and a separate immutable peer should a coordinator-held quiet window run the unchanged hardware transition matrix. Freeze inputs, count actual operations and resources, retain cold/settle/fallback costs and every failed/slow case, and compare frame/presentation cadence separately from JS submission. A fast CSS-transform microbenchmark, a complete 600 ms animation with few frames or success in only cache-hit frames cannot close the existing gate.
